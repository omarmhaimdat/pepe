pepe serve

pepe serve is pepe over HTTP: a script, an agent or a browser starts, watches, steers and compares runs, and pepe worker on other machines takes shares of a run. It sends no load itself: every run is a child pepe, under the server's guardrails, the project's pepe.toml and the machine's settings, exactly as on the command line.

The page

http://127.0.0.1:7878/ is pepe in a browser: the runs, a new run with its plan checked before it starts, a run live (its curves, its verdict as it forms, pause, resume, concurrency and stop), the saved tests and their history, schedules, compare, and the workers. It is one page in the binary, no script from anywhere else. The link pepe serve prints opens it with the token, which the page keeps for the tab and takes out of the address bar; a report opens as a link of its own, with a ticket for that run alone that runs out in ten minutes.

Safe to leave running

  • Loopback by default. --listen takes another address; any but loopback needs --allow-host and the --max-requests, --max-rate and --max-concurrency caps (in the flags, a pepe.toml or the settings), or the server doesn't start.
  • A token on every call but /api/health: made at start and printed, or read from --token-file (name token a line, the name going in the audit log). A header, never a cookie, so a page in a browser can't start a run.
  • The guardrails hold every run. A request can't loosen them: its own guardrail keys only tighten, a value is never read as a flag, and what reaches past them isn't taken (webhook, slack, otlp, a file outside the project).
  • --max-runs (1 by default): runs going at once, here and on the workers; past it, 429.
  • An audit log: who did what, .pepe/serve/audit.jsonl.

Runs

A run takes the arguments pepe mcp's tools do (url, requests, duration, concurrency, rate, warmup, headers, body, method, fail_if, …), with mode for ping, ramp, api, flow or replay, or a saved test by name.

CallDoes
POST /api/runsStarts one: {"url": …, "requests": 1000}, {"mode": "ping", "targets": […]}, {"test": "checkout"} (recorded with the test's runs). 202 and its id
POST /api/runs with "dry_run": trueThe plan, nothing sent
GET /api/runsRecent runs, and how many are going
GET /api/runs/IDHow it stands, and its report once it has one
GET /api/runs/ID/eventsThe run live, as Server-Sent Events: start, progress a second, anomaly, steered, report, end. Last-Event-ID (or ?after=) goes on from there
GET /api/runs/ID/reportThe report: ?format=json (the default), html, md, txt or csv
POST /api/runs/ID/ticketA ticket that opens the run's report as a plain link (?ticket=…), and nothing else, for ten minutes
POST /api/runs/ID/pause · /resume · /stopSteers it; a ping can be stopped
POST /api/runs/ID/concurrency {"n": 40}Held to --max-concurrency

A refusal says why in pepe's words: 422 when a guardrail holds, 400 for what pepe can't run, 409 for what can't be done now.

The same lines come from pepe --events FILE (or - for stdout) on any run, server or not.

Runs started from the server and from the command line are the same files: pepe history NAME lists both.

Workers

A worker joins a server from its own machine, so a run can come from several places at once, and works from behind NAT: it dials out.

  • Its own guardrails hold. A worker runs its share under the flags it was started with, the pepe.toml where it runs and its settings, whatever the server asks.
  • A run shared out: POST /api/runs with "workers": "all" or a list of names. The count, the concurrency and the rate are split among them (a duration is each one's); the run's events carry each worker's, and a progress line a second adds them up.
  • Its report is one run's. Each share's latency histogram comes back whole, and they're added bucket by bucket, so the p99 is the p99 of every request any worker sent. distributed says what each sent.
  • A worker that leaves mid-run ends its share as failed; the run ends on the others, failing. A worker's process killed outright leaves its share's child to the end of its count or its time.
  • GET /api/workers lists them, and what each is busy with.

A plain run and a saved test of one are shared out; the other modes run on the server.

Health

GET /api/health (no token): pepe's version and the reports' schema_version, for a load balancer or a script waiting for the server.
